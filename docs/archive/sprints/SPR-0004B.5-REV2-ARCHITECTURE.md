# SPR-0004B.5 Rev.2 – Modular Service Architecture

## Goal

Rev.2 separates telemetry sources from optional output services.

Sources:
- CAN channel 1
- GPS, when hardware and a valid fix are available

Services:
- AWS IoT
- MQTT
- ABRP

A service can be enabled or disabled without changing CAN decoding. CAN and GPS populate the common telemetry model; services consume that model.

## Capability versus configuration

A service checkbox expresses user intent. Actual availability also depends on the firmware build and credentials:

- AWS requires an AWS-enabled build and provisioned LittleFS credentials.
- MQTT requires an enabled checkbox and a non-empty broker host.
- ABRP requires an enabled checkbox, API key and user token.
- GPS is a hardware capability and remains optional.

## CAN channel model

Current targets expose one operational CAN channel:

- ESP32-WROOM: CAN 1 via ESP32 TWAI
- LilyGO T-A7670: CAN 1 via ESP32 TWAI

The WebUI already displays CAN 2 as reserved and unavailable. No second controller, pin mapping, frame acquisition or decoder dispatch is implemented in Rev.2.

Future rule: each CAN channel may own an independent decoder profile, but decoded telemetry is forwarded without coupling services to the originating bus.

## Configuration migration

Older configurations remain valid:

- MQTT becomes enabled when an old configuration contains a broker host and no explicit service flag.
- ABRP becomes enabled when old credentials are complete and no explicit service flag exists.
- AWS defaults to enabled on AWS builds.

New Preferences keys:
- `svcMqtt`
- `svcAws`
- `svcAbrp`

Configuration export now contains a `services` object.
