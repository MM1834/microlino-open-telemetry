# SPR-0004B.8 – Portal Integration Preparation

## Goal

Prepare the firmware for configuration supplied by the local wizard, JSON clients, and a future portal without removing standalone operation.

## Configuration flow

```text
Factory defaults
Local Wizard / WebUI
REST JSON import
Future Portal
        |
        v
Board ConfigurationManager
        |
        +--> normalize
        +--> validate
        +--> import / export
        +--> save / load / clear
        |
        v
ESP32 Preferences (NVS)
```

The runtime configuration structs remain board-specific because the ESP32-WROOM and LilyGO have different capabilities. The public lifecycle is now identical:

```cpp
manager.load();
manager.save();
manager.clear();
manager.exportJson(includeSecrets);
manager.importJson(json, error);
manager.validate();
```

Concrete managers:

- `AppConfigurationManager` for ESP32-WROOM
- `LilygoConfigurationManager` for LilyGO T-A7670

Only these implementations access `Preferences`. Wizard, WebUI, REST handlers, startup and factory reset use the managers.

## Shared components

Shared code in `firmware/common/config` provides:

- `ConfigurationManager`: board-independent lifecycle contract and normalization helpers
- `ConfigKeys`: canonical JSON field names and schema version
- `ConfigurationReadiness`: board-independent readiness evaluation and serialization

The shared contract does not force both boards into an artificial identical runtime struct. It standardizes the operations that local and future remote provisioning require.

## Transactional import

JSON import follows this sequence:

```text
Parse
  |
Check schema version
  |
Apply supplied fields to current runtime configuration
  |
Normalize
  |
Validate
  |
Save
```

If validation fails, the previous runtime configuration is restored and nothing is written. Fields omitted from an import retain their current values, including secrets. This supports both full backup restore and future partial provisioning payloads.

## Compatibility

Existing routes remain available:

- `GET /api/config/export`
- `POST /config/import`

Canonical portal-ready routes:

- `GET /api/config`
- `POST /api/config`
- `POST /api/config/import`
- `GET /api/readiness`

No portal, login, certificate provisioning, or CloudFormation change is introduced in this sprint.

## Configuration schema

Exports use `schemaVersion: 1` and preserve the existing top-level fields. The schema is additive so older backups without `schemaVersion` remain importable. Imports reject schema versions newer than the firmware understands.

JSON keys are defined once in `config_keys.h`, preventing ESP32 and LilyGO import/export implementations from silently diverging.

Secrets are included by the explicit export endpoint because this preserves existing backup behaviour. These endpoints are local and unauthenticated in B.8; authentication is required before any remote exposure.

## Readiness model

`/api/readiness` returns one board-independent structure with these checks:

- onboarding
- network
- CAN
- GPS
- MQTT
- AWS
- ABRP

`configured` describes whether required configuration is present. `ready` additionally evaluates live network, CAN, and enabled MQTT connectivity. GPS is optional. Disabled services do not block readiness.

The JSON is now serialized with ArduinoJson instead of manual string concatenation.

## Standalone guarantee

The local AP, Wizard, WebUI, MQTT, AWS build variant, ABRP, OTA, factory reset, and existing configuration backup routes remain in place.

## Scope boundary

B.8 does not introduce:

- portal UI or backend
- user or device registration
- fleet provisioning
- certificate lifecycle automation
- second vehicle decoder
- new transport services

Those remain later beta and portal work.
