# REL-001 — Portal Pilot Release Readiness

> **Status:** Active
>
> **Audience:** Maintainer, release reviewer and pilot support
>
> **Started:** 2026-08-03

## Objective

Promote the controlled hosted portal and onboarding implementation from its
feature branch into `develop`, validate one fresh device onboarding, and prepare
the first regular portal release without inventing a separate beta-user class.

## Terminology and environment boundary

- **Pilot user** describes an early, directly supported user. It is not a
  persistent account role or a separate data model.
- `/motbeta/` is the controlled pilot deployment path. It is not a Git branch.
- `develop` is the integration branch for the release candidate.
- `main` represents an accepted repository release.
- There is no `deploy` branch. Deployments must be recorded against an exact
  commit and environment instead of being inferred from a branch name.

Pilot accounts and vehicle assignments may continue unchanged into the regular
release. No migration or re-registration is required merely because the release
label or portal path changes.

## Included scope

- hosted Cognito login/logout and per-user vehicle isolation;
- controlled administrator claim issuance;
- atomic, expiring and single-use portal claim consumption;
- hosted portal configuration and subdirectory-safe OAuth callback;
- exact production-host CORS configuration;
- deployment, validation and pilot-support documentation;
- release reconciliation through `develop` and later `main`.

## Explicitly deferred

- public self-registration;
- device replacement, ownership transfer, loss and recovery automation
  (ONB-001.B3);
- automated certificate provisioning or rotation;
- cloud-managed OTA;
- further LilyGO LTE/GPRS soak, power and recovery qualification beyond the
  completed AWS/LTE functional field test;
- general fleet administration.

Deferred functions must not be presented as available in the release notes.

## Release gates

- [x] Hosted end-user login, vehicle isolation and logout passed.
- [x] Hosted administrator visibility and active-assignment conflict guard passed.
- [x] Effective Cognito callback/logout and exact API CORS values were verified.
- [x] Anonymous and foreign-origin access remain denied by the tested controls.
- [x] Feature branch is pushed with the hosted deployment evidence.
- [x] Canonical redirect from the non-`www` host to `www` is configured or an
      explicit temporary pilot exception is recorded. A bounded hosting exception
      was accepted on 2026-08-03; published auth/API coordinates remain `www`.
- [x] Production hosting access-log treatment for OAuth callback query parameters
  is remediated or a bounded risk acceptance is recorded. CLOUD-017 was accepted
  by the maintainer on 2026-08-03 for directly invited pilot users only; durable
  provider-side remediation remains open.
- [x] One previously unassigned ESP32 is provisioned and claimed end to end with
  no shared or exposed device credentials.
- [x] Support checks cover login, assignment, connectivity, local recovery and
  escalation for the pilot device.
- [x] Full repository test suites pass on reconciled `develop` commit `1e78197`.
- [x] Feature branch is reviewed and merged into `develop` through PR #1.
- [x] `main`-only commits are reconciled through reviewed, content-neutral PR #2.
- [x] Release notes identify included, deferred and known-risk behaviour.

## Promotion sequence

1. Close or explicitly accept the two hosting gaps.
2. Perform the fresh-device pilot onboarding.
3. Update validation, current status and release notes.
4. Review and merge the feature branch into `develop`.
5. Mark and observe a release candidate on the controlled portal.
6. Reconcile `develop` with the current `main` history.
7. Merge the accepted release into `main` and create the final release tag.
8. Promote the portal from its pilot path only after the canonical public path
   and rollback procedure are confirmed.

## Stop conditions

- Do not extend the CLOUD-017 acceptance to public self-registration or a general
  public release; review the provider response or implement durable remediation.
- Do not issue a new device identity without an exact user, vehicle and Thing
  assignment plan.
- Do not remove or overwrite the existing `/dashboard/` portal during pilot
  validation.
- Do not describe ONB-001.B3 lifecycle operations as implemented.
- Do not merge the feature branch directly into `main`.
