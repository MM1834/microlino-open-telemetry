# C6-PH-001 — ESP32-C6 Production Hardening

**Status:** Completed — N16 production-hardening acceptance passed; XIAO compatibility validated

**Started:** 2026-08-07

**Completed:** 2026-08-07

## Objective

Bring the maintained ESP32-C6 firmware to the existing WROOM local-administration
boundary without creating an independent C6 architecture or implementing
WIFI-001's ordered dual-profile logic early.

## Delivered repository scope

- WPA2-protected first-setup and runtime fallback AP;
- authenticated first setup and operational WebUI;
- WiFi configuration plus network, CAN1/CAN2, GPS and AWS diagnostics;
- non-secret backup, authenticated restore and factory reset;
- opt-in local OTA with shared WROOM/C6 authentication, same-origin, abort,
  failure and delayed-reboot behaviour;
- cooperative reconnect while Dual-CAN, GPS, WebUI and AWS loops continue;
- random per-device setup credential and common Web security/OTA core;
- physical `admin recover` USB fallback shared by C6, WROOM and LilyGO;
- all C6, WROOM and LilyGO base/AWS builds.

## Boundaries

- One stored station profile; WIFI-001 owns Home/mobile ordering.
- No remote OTA, Secure Boot, flash encryption or signed fleet rollout.
- XIAO remains a compatibility target, not the selected 16 MB production pilot.
- Compile evidence does not establish production hardware readiness.

## Completion decision

The firmware hardening work package is complete. N16 is the selected pilot target
and passed its full hardware acceptance. XIAO additionally passed build, flash,
WiFi/fallback-AP, authenticated WebUI, GPS and physical administrator-recovery
checks. XIAO vehicle Dual-CAN/AWS equivalence and extended soak remain useful
compatibility evidence but do not block this sprint and remain outside its release
claim.

## N16 acceptance checklist

1. Flash the 16 MB AWS image over USB while retaining NVS/LittleFS credentials.
2. Confirm both TWAI controllers and GPS start before WiFi is available.
3. Interrupt WiFi and verify CAN counters continue while fallback AP starts.
4. Verify authenticated setup/status/config and fail-closed anonymous requests.
5. Exercise backup/restore and factory-reset recovery with test configuration.
6. Perform successful and aborted/invalid OTA tests with USB recovery available.
7. Confirm AWS reconnect and publication after station recovery.

## Repository evidence

- N16/XIAO, WROOM and LilyGO base/AWS PlatformIO builds passed.
- Focused C6/WROOM/LilyGO local-security tests: 25 passed.
- On 2026-08-07 the AWS image was flashed to the selected 16 MB N16 without
  erasing NVS or LittleFS. The device retained WiFi and per-device AWS credentials.
- With both vehicle CAN buses connected and the GPS antenna outdoors, CAN1 and
  CAN2 counters increased concurrently with zero receive errors, GPS reached
  `GPS_FIX`, WiFi reported -48 dBm and AWS IoT remained connected while publishing.
- Removing the mobile hotspot left Dual-CAN and GPS processing active and started
  the WPA2 fallback AP. First setup required its random device credential; after
  setup the AP and WebUI both required the new local administrator password.
- The authenticated WebUI produced a valid non-secret backup. Restore rebooted
  successfully without losing WiFi, local-admin or AWS credential state.
- Local OTA accepted the matching N16-AWS image and rebooted successfully. A
  deliberately invalid `.bin` produced the expected failure page, did not reboot
  and explicitly left the running firmware active.
- After the vehicle left USB/fallback-AP range, the N16 rejoined the configured
  mobile hotspot and resumed AWS publication. DynamoDB contained fresh GPS speed
  telemetry within 17 seconds of the final read-only check.
- The XIAO 4 MB base image retained configuration across USB flashes, connected
  to station WiFi, exposed its authenticated WebUI, maintained a GNSS fix and
  started both CAN controllers. Its fallback AP was physically verified after
  forcing 2.4 GHz channel 1 and removing redundant reconnect calls.
- A lost XIAO administrator password was replaced through the physical
  `admin recover` console command without changing WiFi or decoder settings.
  Login with the generated recovery credential succeeded; the administrator
  then set a new password through the WebUI and successfully authenticated with
  it while all prior device settings remained present.
