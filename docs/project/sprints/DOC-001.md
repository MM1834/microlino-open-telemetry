# DOC-001 — Documentation Consolidation and Beta Baseline

> **Status:** Active
>
> **Owner:** Repository maintainers
>
> **Branch:** `codex/doc-001-documentation-baseline`
>
> **Started:** 2026-07-31
>
> **Base:** `develop` at `ee2c2b4`

## Objective

Create one navigable, code-aligned documentation baseline for the ESP32-WROOM
beta and subsequent portal-onboarding work. Preserve engineering history while
preventing historical sprint notes from being mistaken for current instructions.

## Motivation

The repository contains two documentation generations plus sprint, patch,
validation and release packages. Several documents describe earlier implementation
states, while current interfaces and security boundaries appear in multiple places.
Beta devices and portal onboarding require a smaller, reliable current source set.

## Source hierarchy

DOC-001 uses this evidence order:

1. current code and configuration;
2. accepted current ADRs;
3. reproducible validation against the current commit;
4. governance current status and active work;
5. historical release, sprint and validation records;
6. the future ChatGPT Classic export as audit and reconciliation evidence.

When sources disagree, DOC-001 records the conflict. It does not silently prefer a
historical claim merely because that claim is more detailed.

## In scope

### Documentation architecture

- enforce `docs/DOCUMENTATION_STANDARD.md`;
- maintain one current source of truth per topic;
- add explicit Current, Planned, Historical or Unverified status;
- consolidate navigation for beta users, operators, developers and maintainers;
- maintain a ledger for redirects, retained history and removals.

### Current technical reference

- verify AWS IoT, portal, authentication, REST and WebSocket documentation against
  code and CloudFormation;
- verify firmware, configuration, MQTT topics, CAN, GPS and local-WebUI reference
  against both maintained board implementations;
- distinguish implemented capability from deployed or hardware-validated state;
- resolve ADR numbering collisions and make supersession explicit.

### Beta documentation

- prepare an ESP32-WROOM beta guide for devices with and without GPS;
- document first start, local setup, AWS readiness, diagnostics, backup/restore,
  local OTA, factory reset and recovery;
- prepare a privacy-safe support runbook and support-data checklist;
- prepare device-provisioning and beta-release checklists;
- specify screenshots without treating unverified images as current.

### Historical consolidation

- classify AWS delivery stages, sprint records, patch notes and release notes;
- move durable knowledge into current reference pages;
- retain historical evidence with visible banners and current-document links;
- remove exact duplicates and generated metadata when a canonical copy exists.

## Out of scope

- firmware or backend feature changes;
- PlatformIO environment simplification;
- builds, hardware flashing or OTA uploads;
- AWS deployment or mutation;
- portal onboarding implementation;
- new vehicle decoder implementation;
- final deletion of historically ambiguous material before Chat-export review;
- refreshed UI screenshots before the interface is revalidated.

### DOC-001.1 — Inventory and classification

Classify documents as Current, Planned, Historical, Unverified, Redirect or
Duplicate. Record the canonical owner for each current topic.

### DOC-001.2 — Cloud, portal and security

Consolidate AWS architecture, infrastructure, APIs, authentication, authorization,
credentials and operations. Keep missing user-to-vehicle authorization prominent.

### DOC-001.3 — Firmware and hardware

Consolidate shared firmware, board behaviour, local WebUI, CAN/GPS, configuration,
MQTT/AWS transport and LilyGO LTE status.

### DOC-001.4 — Beta user and support baseline

Create the ESP32-WROOM beta guide, support runbook, provisioning checklist and
release-readiness checklist. Mark steps requiring later hardware or AWS evidence.

### DOC-001.5 — History and navigation

Normalize status banners, redirects, historical locations, ADR navigation and
release/sprint indexes. Update inbound links before moving files.

### DOC-001.6 — Verification and handover

Run link, structure and consistency checks; report unresolved claims; identify the
questions to reconcile against the ChatGPT Classic export.

## Deliverables

- current documentation index by audience;
- documentation standard and migration ledger;
- consolidated architecture, firmware, API and security reference;
- clearly separated historical documentation;
- ESP32-WROOM beta guide with GPS/no-GPS variants;
- beta provisioning checklist;
- support runbook and safe diagnostic-data checklist;
- screenshot specification/backlog;
- DOC-001 validation report;
- Chat-export reconciliation question list.

## Acceptance criteria

- every page reachable from current navigation has status and audience;
- each current topic has exactly one declared source of truth;
- current claims are supported by code/configuration or marked unverified;
- planned portal onboarding is not described as implemented;
- local WebUI and hosted portal responsibilities are not mixed;
- AWS device identity and portal-user authorization are documented separately;
- beta instructions never expose or request private keys, tokens or passwords;
- image references resolve through `docs/assets/images/`;
- all internal Markdown links resolve;
- `git diff --check` passes;
- validation is claimed only when recorded against an exact commit;
- unresolved historical conflicts are listed for Chat-export reconciliation.

## Stop and review gates

### Maintainer review gate

Stop before declaring beta documentation authoritative. Maintainers first review
hardware wiring, provisioning, recovery and support procedures.

### Chat-export gate

Stop before deleting or rewriting historically ambiguous decisions, validation
claims or hardware rationale that cannot be resolved from code and Git history.
Use the ChatGPT Classic export to confirm or correct those items.

### Implementation gate

DOC-001 may prepare ONB-001 inputs but must not implement onboarding. ONB-001 begins
only after the documentation baseline and authorization risks are reviewed.

## Validation policy

DOC-001 starts with non-mutating static inspection. Builds, device tests and
read-only AWS inventory require separate explicit approval and become additional
evidence rather than being inferred from historical artifacts.

## Risks

- file moves may break external links;
- stale screenshots may appear authoritative;
- historical notes may conceal that current head was never tested;
- early duplicate removal may discard rationale;
- documentation cleanup can accidentally broaden product scope.

Mitigation is incremental migration, explicit status, small reviewable commits and
preserved Git history.
