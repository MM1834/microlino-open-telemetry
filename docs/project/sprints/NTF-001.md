# NTF-001 — Charging and SOC Notifications

> **Status:** Completed — bounded email/portal pilot accepted; SMS deferred
>
> **Date:** 2026-08-07

## Objective

Add optional per-user and per-vehicle email and SMS notifications when a
configured SOC target is reached while charging. The default target is 80%. A
notification is informational only and never controls or interrupts vehicle
charging.

## Product boundary

NTF-001 consumes normalized cloud telemetry and does not add notification logic
to firmware. Each authenticated portal user configures notifications separately
for each vehicle they are authorized to access. Notification destinations are
independent of the Cognito account email address.

The first portal settings slice is deliberately user-facing. Fleet-wide
administration, impersonation, support access and general account preference
management remain separate work.

## User settings

The settings model is keyed by the authenticated Cognito `sub` and `vehicleId`.
It includes:

- enabled/disabled state;
- target SOC percentage, default 80%;
- email and SMS channel selection;
- notification email address, which may differ from the account address;
- mobile number in E.164 form;
- destination verification/subscription state;
- created and updated timestamps.

Users may read or update preferences only for vehicles currently authorized to
them. Revoked vehicle access must prevent preference reads, writes and delivery.
Contact destinations are sensitive personal data and must not appear in normal
logs, audit messages, AWS resource tags or unauthenticated responses.

## Trigger contract

A notification event is eligible only when:

1. the vehicle is plugged in;
2. the current charging session has observed credible charging activity;
3. a valid SOC below the configured target was observed in that session;
4. a later valid SOC reaches or exceeds the target while the session remains
   active; and
5. that user, vehicle, target and session have not already produced an event.

The session survives short charging pauses and ends on credible unplugging.
Starting or reconnecting above the threshold must not create a notification.
Regeneration while driving must not count as charging. Delayed, stale and
out-of-order telemetry must fail safely. Conditional persistence or an equivalent
idempotency mechanism must prevent duplicates across Lambda retries and process
restarts.

## Message contract

Every message includes:

- the portal vehicle name when available;
- the canonical `vehicleId`;
- reached SOC and configured target;
- event time in the user's displayed time zone where available; and
- a short statement that the notification is informational and does not control
  charging.

SMS text must remain within one segment where practical. Email and SMS delivery
derive from the same stored notification event so enabling both channels does not
run the threshold detector twice.

## Delivery and cost boundary

Amazon SNS is the pilot delivery service for both channels.

- Email requires explicit destination confirmation.
- SMS initially operates only with controlled, verified sandbox destinations.
- SMS has a low enforced account spend limit and a CloudWatch alarm.
- Provider message IDs are correlated with privacy-safe notification event IDs.
- Daily SMS usage reports are retained only for a bounded operational period and
  reconciled to delivery count and actual provider cost.

AWS charges remain on the project AWS account. Per-user cost allocation,
chargeback, invoicing, tax handling and payment collection are explicitly outside
NTF-001 and remain backlog work.

## Acceptance gates

- settings are default-off and isolated by existing vehicle authorization;
- default target is 80% and invalid targets/destinations are rejected;
- a destination different from the Cognito email can be configured and verified;
- one rising crossing produces at most one logical event per user, vehicle,
  target and charging session;
- stationary startup above target, telemetry replay, Lambda retry, reconnect and
  driving regeneration produce no duplicate or false notification;
- email and SMS identify the correct vehicle when a user owns multiple vehicles;
- channel unsubscribe/disable takes effect before later delivery;
- SMS is bounded by sandbox verification, an enforced spend limit and an alarm;
- delivery logs exclude plaintext email addresses, telephone numbers and message
  bodies and expire after a documented retention period;
- notification failures cannot fail state ingestion, history or live portal
  fan-out;
- local authorization, detector, idempotency, API and portal tests pass;
- controlled live email and SMS acceptance is recorded before the pilot is called
  operational.

## Repository evidence

On 2026-08-07 the pure charging-session state machine was added under
`cloud/aws/notifications/`. Seven focused tests pass for a valid rising crossing,
startup above target, driving regeneration, a short charging pause, unplugging,
replayed SOC and invalid SOC. The existing 17 foundation authorization tests also
remain green. DynamoDB persistence, SNS delivery, portal settings and deployment
were not yet claimed at that checkpoint.

Later on 2026-08-07 an independent `mot-dev-notifications` CloudFormation stack
was packaged into the existing MOT artifact bucket, reviewed as an additive-only
Change Set and reached `CREATE_COMPLETE`. It adds notification preference,
session and 31-day TTL event tables, an isolated IoT/Lambda consumer, a filtered
SNS email topic and a JWT-protected GET/PUT preference API. The existing Vehicle
API health route remained 200 and the unauthenticated preference route returned
401. The controlled `pioneer` preference is enabled at 80%, and its SNS email
subscription was confirmed by the recipient and read back as active. SMS is
disabled because AWS returned `SubscriptionRequiredException` for the account's
SMS service. No portal UI, delivered threshold notification or live charging
crossing is claimed yet. The notification Lambda had 833 invocations without
logged errors at the confirmation checkpoint. Its session table contained only
the currently publishing legacy `xrpioneer` identity; the last stored `pioneer`
SOC/charging/plugged timestamps predated the notification deployment.

The subsequent physical `pioneer` charging test started below the temporary 60%
target with `plugged=true`, `is_charging=true` and an armed session at SOC 58%.
Crossing to 60% produced exactly one persisted event with status `DISPATCHED` and
exactly one SNS email delivery. The recipient confirmed that SOC and `vehicleId`
were present in the received message. No premature or duplicate event was stored,
and the temporary target was restored to the intended 80% default after the test.

The first portal settings slice is implemented in the repository for the selected
authorized vehicle. It loads and saves enabled state, target SOC and notification
email through the dedicated JWT API, shows confirmation state and leaves SMS
visibly unavailable while the account remains on the AWS Free plan. The deployed
API update preserves a stored phone destination when the SMS field is absent and
normalizes DynamoDB numeric values before JSON serialization. JavaScript syntax,
Python compilation, 11 notification tests, 17 existing foundation authorization
tests and `git diff --check` pass.

A later pilot-handoff refinement now explains directly in the portal that the
mandatory subscription message is sent by `AWS Notifications`, may not mention
MOT, requires the `Confirm subscription` action and may be found in the spam
folder. The help is hidden after the API reports `emailConfirmed=true` and becomes
visible again immediately when the confirmed address is edited. The SNS topic
source also defines the display name `Microlino Open Telemetry` for regular
notification messages. AWS does not apply that display name to its service-owned
subscription confirmation message, and the confirmation process itself remains
unchanged. On 2026-08-20 the minimal CloudFormation Change
Set `mot-notification-display-name-20260820` modified only `EmailTopic.DisplayName`,
reported `Replacement: False` and reached `UPDATE_COMPLETE`; the effective topic
attribute reads `Microlino Open Telemetry`. The matching hosted `index.html`
and `js/app.js` were uploaded manually through the controlled FTPS path. Public
source verification confirmed the explanatory text, cache-busted script and
conditional hide/edit logic; the maintainer then successfully accepted the
confirmed-address behaviour in the hosted portal. This refinement does not alter
the completed NTF-001 delivery or confirmation process.

On 2026-08-08 the portal slice was uploaded. Initial acceptance exposed two
deployment-configuration gaps: the hosted `config.js` first omitted the dedicated
notification API endpoint, and the notification stack still allowed the former
`microlino-logbook.com` origin. The production config was corrected and the live
stack origin changed to `https://www.microlino-open-telemetry.ch`. Direct GET and
PUT CORS preflights then returned HTTP 204 with the exact production origin and
the required authorization/content-type headers. The maintainer then successfully
loaded the stored `pioneer` preferences and saved several different SOC targets
through the authenticated production portal. This closes the NTF-001 email and
portal pilot; SMS remains an explicitly deferred channel.
