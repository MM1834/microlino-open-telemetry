# LTE-001 — LilyGO LTE Resilience

> **Status:** Parked — functional hardware baseline retained; extended qualification deferred
>
> **Started:** 2026-08-04

## Objective

Harden the functionally validated LilyGO A7670 AWS IoT path without changing
telemetry topics, per-device AWS identity, vehicle isolation, local portal/WebUI
operation or the WiFi-only ABRP boundary.

## Baseline and risks

The repository already preferred WiFi and used A7670 LTE/TLS as AWS IoT fallback.
The 2026-08-03 field test proved the functional path, but inspection found:

- network registration could block the main loop for 60 seconds per retry;
- retries used a fixed cadence and had no escalation after repeated failures;
- a cached GPRS flag could report success briefly after the modem detached;
- a Swisscom-specific APN was silently restored when configuration was empty;
- APN username/password existed in storage/import but were not editable in the UI.

## Implemented slice

- LTE is explicitly disabled until an APN is configured; there is no provider
  default for new or reset devices.
- APN username and password are configurable in the authenticated local WebUI;
  the stored password is never rendered and a blank submission preserves it.
- registration retries are bounded to 15 seconds during normal operation and use
  exponential backoff from 15 seconds to 5 minutes.
- modem initialization no longer opens packet data before the preferred WiFi path
  has been evaluated.
- four consecutive registration/PDP failures trigger one modem power/init recovery
  before the backoff-controlled retry cycle continues.
- network and modem diagnostics expose LTE configuration, current retry interval,
  failure count and recovery count.
- WiFi remains preferred; AWS X.509 credential loading, Thing/client identity,
  vehicle topic isolation, telemetry payloads and ABRP behaviour are unchanged.

## Verification boundary

Validated on 2026-08-04:

- 11 focused LTE/local-security source tests passed;
- `lilygo-t-a7670` compiled at 53,540 bytes RAM and 1,096,077 bytes flash;
- `T-A7670X-AWS` compiled at 54,008 bytes RAM and 1,147,997 bytes flash.
- the AWS build was flashed without erasing NVS or LittleFS; the existing local
  configuration, Thing identity and per-device AWS credentials were retained;
- after the configured WiFi was removed, the device observed the grace period,
  registered the A7670G on mobile data using the configured APN, received an LTE
  address and reconnected AWS IoT over LTE/TLS as `mot-lilygo-fe8ce0` for vehicle
  `pioneer`;
- LTE and AWS IoT remained connected through the observed periodic attempt to
  return to the unavailable preferred WiFi network.
- when the preferred WiFi returned, AWS IoT selected its WiFi TLS transport,
  reconnected with the same Thing identity and the network manager reported
  `192.168.100.124` at RSSI -30 dBm. This completed one observed
  WiFi-to-LTE-to-WiFi round trip.

Maintainer-reported road validation on 2026-08-04 additionally confirmed:

- automatic WiFi-to-LTE transition while driving;
- expected recovery after a period with no mobile-network coverage;
- expected startup and reconnection after a complete power-off/power-on cycle;
- continued expected operation of the exercised telemetry/AWS path.

ABRP remained WiFi-only by design and was therefore unavailable over LTE during
the drive.

The complete tools test suite ran 76 of 77 tests successfully. Its one failure is
outside LTE scope: an existing dashboard cache-buster assertion expects
`20260803-4`, while the concurrently modified dashboard references `20260804-1`.

Long-duration soak, controlled weak-signal thresholds, SIM removal/restore and
repeated transition-cycle tests remain necessary before production qualification.
The periodic WiFi return attempt still performs an approximately eight-second
bounded station wait in the main loop; replacing it with event-driven WiFi
reassociation remains a resilience improvement.

## Parking decision — 2026-08-09

The validated LilyGO/A7670 implementation remains available as a sustain-only
baseline, but its extended production qualification is no longer active work.
Near-term firmware development is concentrated on the shared ESP32-C6 line.
Resume the parked tests or add LilyGO-specific features only after an explicit
priority decision; maintenance and regression fixes remain permitted.
