# OPS-001 — Lambda Capacity and Portal Resilience

> **Status:** Active — regional quota restored; isolation acceptance open
>
> **Opened:** 2026-08-24

## Objective

Prevent high-frequency telemetry and notification processing from exhausting the
regional Lambda concurrency pool used by interactive Vehicle, History and
Notification APIs. Preserve correct portal state through short capacity failures
without weakening authorization, notification idempotency or telemetry ordering.

## Trigger and measured baseline

During simultaneous onboarding and active telemetry on 2026-08-24, the portal
temporarily showed empty notification settings and failed History refreshes for
`xrpioneer2`. Read-only inspection proved that the stored access, History and
preference records remained intact.

CloudWatch identified the shared boundary:

- effective regional Lambda concurrent-execution quota: 10;
- account concurrency: 10/10 continuously from 20:03 through 20:09 CEST;
- account throttles: 385–620 per minute during that interval;
- state ingest reached concurrency 10 and 190–314 throttles per minute;
- notification processing reached concurrency 7–8 and 195–304 throttles per
  minute;
- Vehicle and Notification APIs each returned a transient 5xx at 20:06;
- DynamoDB History and preference tables were `ACTIVE`, `PAY_PER_REQUEST` and
  showed no read throttling.

## Delivery slices

### OPS-001.A — Portal partial-failure resilience

- retry authenticated GET requests twice for HTTP 429/500/502/503/504 with short
  exponential backoff;
- never retry mutating POST or PUT requests automatically;
- load preference and SMS status independently;
- retain a successfully loaded channel when the other channel fails;
- label unavailable state as temporary instead of presenting it as unconfirmed.

The chart History request and the personal 30-day range forecast are now separate
authorized API calls. Range switching no longer repeats the forecast's three raw
30-day queries, a forecast failure cannot blank the diagrams, and the portal
deduplicates forecast loads per selected vehicle.

The replacement-free Foundation update reached `UPDATE_COMPLETE`. Hosted
`motbeta` and production `/dashboard/` acceptance subsequently passed on desktop
and smartphone with two users. This closes the History/forecast resilience slice;
the wider asynchronous-workload isolation work below remains independent.

### OPS-001.B — Regional quota recovery

- raise the effective Lambda concurrency from the exceptional value 10;
- record request ID, effective value and approval status;
- verify the new effective quota before deploying concurrency reservations.

The exceptional effective value of 10 initially caused AWS to reject a request
for 100 because its quota workflow compared against the nominal default 1,000.
After explicit maintainer approval, request
`f264d9016cab4178b782ed315413fa8b1DzGq1fA` requested 1,001 and opened support
case `178759663200182`. Live read-back on 2026-08-25 now reports an effective
regional quota of 1,000, so the ten-execution capacity gate is closed.

### OPS-001.C — Workload isolation

- filter the Notification IoT Rule to the exact charging, journey, SOC, speed,
  odometer, power and online suffixes before Lambda invocation;
- preserve headroom for Vehicle, History, Preference and SMS Verification APIs;
- buffer high-frequency asynchronous telemetry consumers before applying a hard
  worker-concurrency cap;
- use a DLQ and observable queue age/depth rather than dropping excess events;
- avoid reserved-concurrency deployment until the regional quota can retain safe
  unreserved capacity;
- alarm on account Lambda throttles and sustained concurrency saturation.

The idempotent operator script
`tools/aws/deploy_ops_001_capacity_alarms.sh` deploys two account-level alarms to
the already confirmed `mot-dev-sms-operations` topic. After quota recovery, the
concurrency warning is 800 (80% of the live 1,000 quota). Both alarms notify only
on `ALARM`; `OK` actions are intentionally absent to prevent recovery-message
floods during metric flapping. The throttle alarm continues to report any
regional Lambda throttle.

The existing direct state-ingest and notification IoT rules are not changed live
until the queue envelope, ordering/idempotency behaviour, rollback and no-loss
Change Set have passed focused tests.

The narrower pre-invocation Notification Rule filter is deployed independently.
Its first exact one-resource Change Set used SQL-style parenthesized `IN` values;
AWS IoT rejected that syntax and CloudFormation returned safely to
`UPDATE_ROLLBACK_COMPLETE` with the original rule. Version 2 uses AWS IoT array
literals, again modified only `NotificationRule` without replacement, and reached
`UPDATE_COMPLETE`. Live read-back contains the exact charging, display, BMS,
status and journey clauses. In the first full minute after activation,
notification invocations fell from 187–206/minute to 4 and notification throttles
from 115–139/minute to 5. Account throttles fell from 225–265/minute to 18, but
account concurrency still reached 10/10; quota approval and state-ingest
isolation therefore remain necessary.

## Acceptance gates

- [x] Stored `xrpioneer2` data and authorization confirmed intact.
- [x] Lambda concurrency saturation and principal consumers measured.
- [x] Portal retries transient read failures without retrying writes.
- [x] Preference and SMS state render independently on partial failure.
- [x] Notification Rule filtering prevents irrelevant telemetry from invoking the
  notification Lambda in the repository template.
- [x] Account throttle and near-saturation alarms are deployed to the confirmed
  operations destination.
- [x] Minimal NotificationRule-only Change Set is deployed without replacement;
  effective SQL read-back passes.
- [x] Lambda quota increase request is accepted into an AWS Support case.
- [x] Effective regional concurrency is safely above the ten-execution pilot cap.
- [ ] Interactive API headroom is protected from asynchronous telemetry bursts.
- [ ] Queue/DLQ alarms are deployed and confirmed for any later queue migration.
- [ ] Hosted desktop and smartphone acceptance passes under a controlled injected
  5xx and during normal live telemetry.
- [ ] No telemetry, notification idempotency or authorization regression is
  observed.

## Cost and safety boundary

A concurrency quota or reservation has no standing charge; normal invocation and
duration charges still apply. Provisioned Concurrency is outside this sprint.
Queue, DLQ and alarm costs must be measured but are expected to remain small at
pilot volume. Capacity changes never bypass SMS spend, country, sender, approval,
rate or alarm gates.

## Rollback

Portal read retries and independent rendering can be reverted by restoring the
previous static assets. Any later queue migration retains the former direct IoT
rule disabled but recoverable until acceptance closes; rollback must never run
both paths simultaneously because that would duplicate state transitions and
notifications.
