# SMS-001 — Controlled SMS Notification Pilot

> **Status:** Active — analysis and cost gate
>
> **Date:** 2026-08-24

## Objective

Activate a bounded SMS channel for the existing SOC-target and qualified
charging-interruption events. AWS service activation, administrator approval,
destination-country and origination-identity allowlisting, an enforced spend
limit and an operational alarm are one indivisible release package. No subset may
make SMS delivery effective.

SMS remains informational and never controls charging or the vehicle. Existing
email delivery, telemetry ingestion, History and live portal delivery must remain
independent of every SMS failure.

## Current baseline

The deployed `mot-dev-notifications` stack already stores per-user/per-vehicle
preferences and idempotent notification events. The portal deliberately forces
`smsEnabled=false`. The backend contains a legacy direct SNS phone publish guarded
only by `smsEnabled && smsConfirmed`; it has no administrator approval, country,
approved-originator or deployment-wide enablement check and therefore is not an
acceptable activation path.

On 2026-08-24 AWS End User Messaging SMS access in `eu-north-1` returned
`SubscriptionRequiredException`. A subsequent authenticated console check showed
the account still on the AWS Free account plan and directed it to complete
registration or upgrade the plan. The IAM maintainer session could not open the
plan-upgrade page. There is no live SMS send, approved originator or SMS cost
evidence yet.

## Indivisible activation gates

Delivery is allowed only when every gate below is true at send time:

1. the AWS account and `eu-north-1` have usable SMS sandbox or production access;
2. a stack-level kill switch is explicitly enabled;
3. the destination is normalized E.164, AWS-verified where required and maps to
   an allowed country (initially only `CH`, `+41`);
4. the request uses the one configured and approved origination identity; callers
   cannot select or override the sender;
5. an administrator-owned allowlist entry matches the user, vehicle, channel and
   destination fingerprint and is active;
6. the user has explicitly opted in and has not disabled SMS;
7. an enforced monthly SMS spend limit is configured and read back successfully;
8. a CloudWatch alarm on `AWS/SMSVoice:TextMessageMonthlySpend` is `OK`, has a
   confirmed operational destination and is below its earlier warning threshold;
9. the existing event idempotency and event-specific delivery limit allow the
   send.

Missing, stale or unreadable gate state fails closed. An ordinary preference PUT
must never be able to create or modify administrator approval. Turning SMS off
remains self-service and takes effect immediately.

## Recommended AWS path

Keep SNS topics for email, but use the AWS End User Messaging SMS v2 API for the
SMS side with a fixed configuration set, Protect configuration and explicit
origination identity. This makes country and sender selection visible and
testable at the send call instead of relying only on account-wide SNS defaults.

The initial Protect configuration blocks every country and allows only
Switzerland. `Allow`/`Block` mode has no Protect surcharge; `Monitor` or `Filter`
would add USD 0.01 per evaluated message and is unnecessary for the first exact
allowlist pilot. The application also validates `+41`; the AWS rule is a second
boundary, not a replacement for application validation.

Switzerland supports sender IDs according to the current AWS country matrix. The
pilot should request `MOT` or another approved maximum-11-character identity,
record the effective AWS identity and its resource policy, and reject deployment
configuration containing any other identity. If AWS or a carrier substitutes the
displayed sender, that observed behaviour must be documented before wider rollout.

## Administrator approval model

Use a dedicated approval record rather than a user-writable boolean in the
preference payload. Minimum fields are:

- `userSub`, `vehicleId`, channel and active/revoked state;
- SHA-256 destination fingerprint, never a plaintext phone number in an audit log;
- allowed ISO country and approved originator identifier;
- approving administrator, reason, creation, expiry and revocation timestamps;
- an optimistic version or conditional write for auditable changes.

The first slice needs an authenticated least-privilege administrator CLI or
runbook, not a general admin portal. Approval must be reissued after a phone-number
change and revoked automatically when vehicle access is no longer `ACTIVE`.

## Spend and alarm boundary

The pilot starts in the AWS SMS sandbox where practical: AWS currently limits the
account to USD 1 per month, permits at most ten verified destinations and charges
normal SMS rates after the first verification message. Request production access
only after controlled sandbox acceptance.

The initially recommended production ceiling was USD 5 per calendar month. Live
pilot reconciliation superseded it on 2026-08-25 with an approved USD 10 ceiling
and USD 6 warning boundary, with:

- an enforced End User Messaging text-message spend limit of USD 10;
- a CloudWatch warning at USD 6 (60%) on the `Maximum` statistic;
- an operational SNS/email alarm destination confirmed before SMS enablement;
- a second application rate boundary of at most one SMS per logical event and no
  more than ten SMS per destination per rolling day;
- a deployment kill switch that can stop SMS without affecting email;
- bounded privacy-safe delivery events containing provider message ID, parts,
  status and actual provider price where available.

The spend limit is not an exact hard cap: AWS documents that distributed SMS
publishing can continue for minutes after a quota is crossed. The lower alarm and
application rate limit therefore provide necessary headroom.

## Cost analysis

AWS's 2026-08-24 downloadable price list quotes **USD 0.05124 per outbound SMS
message part to Switzerland, all networks and number types**. Costs are per part,
not per logical message. GSM-7 text normally allows 160 characters for one part;
Unicode or concatenation reduces the available characters. Pilot messages must
be normalized to an ASCII/GSM-7-safe, single-part template and verified from
delivery events.

Illustrative monthly transport cost, excluding tax and currency conversion:

| Pilot volume | Message parts | SMS transport |
|---|---:|---:|
| Controlled acceptance | 10 | USD 0.51 |
| 10 users × 6 events | 60 | USD 3.07 |
| 25 users × 10 events | 250 | USD 12.81 |
| 100 users × 10 events | 1,000 | USD 51.24 |

With the approved USD 10 enforced ceiling, the theoretical single-part capacity
is 195 messages before overshoot headroom; operationally the USD 6 alarm fires at
about 117 parts. One standard-resolution CloudWatch alarm is approximately USD
0.10 per month before any applicable free tier. Existing Lambda, DynamoDB and
log increments are expected to be cents at pilot scale, but must be measured
rather than booked as zero. A dedicated leased number, two-way messaging and SMS
Protect `Monitor`/`Filter` are not in the initial budget.

There is no end-user chargeback. AWS continues to bill the project account.

## SMS-001.C deployment evidence

The repository adds a dedicated `mot-dev-sms-approvals` table keyed by
`vehicleId + userSub`, a separate `mot-dev-sms-approval-audit` table and the
principal-bound `mot-dev-sms-approval-admin` role. Both tables are encrypted,
PAY_PER_REQUEST and use `expiresAt` TTL; audit retention is 90 days. Neither
notification Lambda role nor the user Preference API role gained access to the
approval tables.

The operator CLI plans by default, accepts only Swiss `+41` destinations, stores
only a SHA-256 destination fingerprint, validates current `ACTIVE` vehicle access
and assumes the dedicated role. Approval/renewal and revocation each mutate the
current record and append an audit event in one conditional DynamoDB transaction.
Optimistic versions reject stale concurrent changes. The normal input path uses a
non-echoing prompt so a telephone number need not enter shell history; normal and
error output redact the subject and plaintext destination.

Fifty-three Notification/Journey tests and seven focused administrator tests
pass. AWS CloudFormation validation passes with `CAPABILITY_NAMED_IAM`. The first
Change Set was rejected before execution because stack-tag and packaging drift
made it unnecessarily broad. The replacement Change Set
`sms-001-c-minimal-20260824` contained exactly three `Add` actions and no Modify,
Replacement or Delete: the approval table, audit table and admin role. It was
executed and the stack reached `UPDATE_COMPLETE`.

Live read-back confirms both tables `ACTIVE`, encrypted, PAY_PER_REQUEST, TTL
enabled and empty. The inline role policy names only the access, preference,
approval and audit tables with the required item actions; `MartinMOT` successfully
assumed the role. A deliberately unauthorized CLI probe failed with
`user does not have ACTIVE vehicle access`, after which both tables still had
zero items. No real approval or SMS delivery was created.

## SMS-001.E repository evidence

The repository now separates destination verification from both ordinary
preference writes and administrator approval. An authenticated vehicle user can
enter only a Swiss `+41` number, request the AWS sandbox verification code and
confirm it in the portal. A dedicated Lambda role can read current vehicle
access and approval status, update only the encrypted preference and shared
destination registries, and call only the three required End User Messaging
verification operations. It cannot create or change an administrator approval.

The shared destination registry is keyed by the SHA-256 number fingerprint and
contains the AWS verified-destination identifier and state, but no plaintext
number. This permits one verified number to be reused for several vehicles or
users without a second verification SMS. The portal does not disclose that a
number is shared. Activation remains per user and vehicle: the checkbox is
available only when the shared number is verified and an unexpired approval
matches the exact user, vehicle and fingerprint. Changing the displayed number
immediately disables the checkbox and requires the matching lifecycle again.

The ordinary preference API accepts SMS enablement only for a currently
confirmed, unchanged Swiss destination. This is a user opt-in boundary, not a
delivery authorization: the later SMS-001.D dispatcher must independently
re-evaluate verification, exact administrator approval, country, sender, spend,
alarm, rate, idempotency and kill-switch gates at send time.

Sixty notification backend tests and 25 administrator/dashboard contract tests
pass, along with Python and JavaScript syntax compilation and whitespace
validation.

The reviewed Change Set `sms-001-e-20260824` added the destination table,
verification Lambda and role, integration, three JWT routes and invoke permission;
it modified only the existing API's CORS methods without replacement. No existing
Lambda, table, role or route was replaced or deleted. A second reviewed Change Set
`sms-001-e-preference-20260824` updated only the existing preference Lambda and
its replacement-free API integration so the confirmed-Swiss-number opt-in guard
is live. Both updates reached `UPDATE_COMPLETE`.

Live read-back shows `mot-dev-sms-destinations` `ACTIVE`, encrypted,
PAY_PER_REQUEST, TTL-enabled and empty. The verification Lambda is active and its
role has only exact access/approval reads, preference/destination item access and
the three required SMS verification actions. An unauthenticated direct Lambda
probe returned 401 without a function error, the public verification route
returned HTTP 401 without a JWT, the destination table remained empty and AWS
still reports zero verified destination numbers. No code or SMS was sent. The
portal source is not yet uploaded to the hosted dashboard.

The first hosted verification attempt exposed one least-privilege integration
error: optional tags in `CreateVerifiedDestinationNumber` implicitly required
`sms-voice:TagResource`, which the verification role correctly did not allow.
AWS created neither a destination nor an SMS. The tags were unnecessary and were
removed instead of broadening IAM. The reviewed Change Set
`sms-001-e-tagfix-20260824` modified only the verification Lambda and its
replacement-free integration; the stack returned to `UPDATE_COMPLETE` with the
new function active.

The next attempt created the controlled Swiss destination as `PENDING`, but AWS
revealed that verification-code delivery internally also authorizes
`sms-voice:SendTextMessage` against the selected origination identity. A reviewed
follow-up granted that action only on the exact `MOT/CH` sender ARN. The code then
arrived and the maintainer confirmed it in the portal; AWS reports the destination
`VERIFIED`. The first exact 30-day administrator approval for the controlled
`pioneer` user association was planned and then written atomically with its audit
event as version 1. No notification SMS has yet been enabled or sent.

The first post-approval portal save exposed a client-side ordering defect: the
busy-state render restored stale `smsEnabled=false` before the form payload was
read, so the API correctly saved false while the UI reported `Gespeichert`. The
repository fix captures the complete form payload before the busy render and
reconciles the returned SMS state. It also hides the verification-code field
unless a code is actually `PENDING`; changing a number alone does not show it
until the user requests a code. Nineteen dashboard contract tests and JavaScript
syntax checks pass. Hosted upload and repeated opt-in acceptance remain pending.

## SMS-001.D deployment evidence

The deployed dispatcher now sends SMS only for SOC-target and qualified
charging-stop events; journey summaries remain email-only. Every SMS attempt
requires the deployment kill switch, Swiss `+41` format, single-part ASCII text,
exact active user/vehicle/fingerprint approval, shared destination verification,
the live USD 1 enforced text spend limit, the named spend alarm in `OK`, the
fixed `MOT/CH` sender and configuration set, event idempotency and a conditional
maximum of ten messages per destination/day. Rejection is stored as privacy-safe
delivery evidence and cannot fail an independent email delivery.

The first reviewed Change Set added the encrypted, TTL-enabled, PAY_PER_REQUEST
rate table and deployed the dispatcher with its kill switch false. Live read-back
confirmed the empty table and exact IAM. The activation review then removed the
historical SNS wildcard publish permission; SNS publish is now restricted to the
email topic, while SMS send is restricted to the exact `MOT/CH` sender ARN. The
second reviewed Change Set activated the kill switch without replacing any table
or function. Stack and Lambda are healthy, the spend limit is USD 1, the USD 0.60
alarm is `OK`, destination is `VERIFIED`, approval is active and the previously
suspended Pioneer user opt-in is restored. Sixty-two backend tests pass. Physical
end-to-end application acceptance and cost reconciliation remain SMS-001.F.

The first physical qualified charging-stop event at 93% against the 100% target
delivered its email but recorded SMS `REJECTED/PROVIDER`. All application gates
had passed and the rate record incremented once. A matching direct provider call
then succeeded, and the maintainer confirmed handset receipt at 13:23. This
isolated the failure to Lambda IAM: normal sandbox send authorization required
the exact verified-destination and configuration-set resources in addition to
the exact sender. A reviewed Change Set added only those explicit resources; the
stack returned to `UPDATE_COMPLETE`. Transport, `MOT/CH` sender path, Protect
configuration and message format now have handset evidence. Because the original
event is idempotently closed, end-to-end Lambda delivery still requires a new
charging session.

The subsequent SOC-target test passed end to end: crossing 97% in the controlled
Pioneer session stored one idempotent event with both email and SMS `SENT`, and
the maintainer confirmed receipt of both channels. A second charging stop in that
same still-plugged session correctly produced no new event because the earlier
93% stop had already consumed the one-stop-per-plug-session idempotency key. A
fresh unplug/replug session remains required to validate charging-stop SMS after
the IAM correction. The destination/day application counter is 2: the original
provider-rejected attempt and the successful SOC send; the direct diagnostic send
did not pass through the application counter.

The product wording now makes the established idempotency boundary explicit:
there is at most one charging-stop notification per continuously plugged session.
Only unplug/replug starts a new session; intermittent top-up while still plugged
does not. This intentionally suppresses repeated alerts during multi-hour or
multi-day connection with solar zero-export control, load management or other
external charging pauses.

On 2026-08-25 the first live cost reconciliation showed USD 0.61488. This
correctly moved the USD 0.60 alarm to `ALARM` and blocked further application SMS
without affecting email. The maintainer approved a USD 10 monthly ceiling and
USD 6 warning threshold. AWS initially rejected the direct override because both
enforced and maximum limits still read USD 1. Service Quotas accepted request
`c52b7741a4e942cb89dc4e65a33e793afkks4KMb` for `TextMessageMonthlySpend`
quota `L-2325465C` and opened support case `178763910400803`.
On 2026-08-26 the maintainer added the requested operational context to that
case: transactional SOC-target and qualified charging-stop messages only, no
marketing, explicit opt-in and verification, exact association approval, CH/DE
Protect boundary, idempotency, ten-per-destination/day rate limit, kill switch,
sub-100-part expected monthly volume and the planned USD 6 warning. AWS review
was then the only gate to the USD 10 provider maximum.
For continued tightly bounded pilot use, the alarm was raised temporarily to USD
0.90 on 2026-08-26 after confirming unchanged spend of USD 0.61488. Its stale
state was explicitly returned to `OK` with that measured value recorded in the
reason; the next provider datapoint resumes normal evaluation. There is no `OK`

AWS approved the account for production access and a USD 50 maximum monthly text

Germany (`+49`). Portal, preference API, verification API, administrator CLI and
dispatcher derive the country from the normalized prefix and use separate exact

The account-default Protect configuration now reads `ALLOW` for CH and DE while
all other countries remain blocked. The reviewed CloudFormation Change Set
updated only the existing Lambda code, roles and integrations without replacing

administrator/dashboard tests pass.

The requested Swiss pilot identity `xruser` resolves to active vehicle
`xrpioneer2`; the older `xrpioneer` assignment is `REVOKED` and remains untouched.
The user subsequently entered and confirmed a Swiss `+41` number, enabled SMS

The DE boundary is preparation for a separate future user who is not yet

## Acceptance

- a deployment with any missing gate produces no SMS;
- a normal user cannot set or retain administrator approval; the portal may show
  only whether its own exact vehicle association is ready or still awaiting
  approval, never approval details or another association;
- a changed destination invalidates prior approval and verification;
- non-CH destinations and any unapproved sender fail before the provider call;
- the Protect configuration independently blocks all non-CH countries;
- the spend limit, USD 6 warning alarm and confirmed alarm destination are read
  back before the stack-level SMS switch can be enabled;
- retries produce no second SMS for the same logical notification event;
- rate and spend rejection cannot change an email event into a backend failure;
- plaintext phone numbers and message bodies do not enter routine logs or audit
  records;
- one controlled target-reached and one qualified charging-stop SMS reach the
  approved handset, stay within one part and reconcile to provider cost;
- disabling or emergency-killing SMS prevents later sends without redeployment.

## Cost-sensitive decisions still requiring live evidence

- whether the approved Swiss sender ID is displayed consistently by the pilot
  carriers or AWS substitutes a shared originator;
- whether standard End User Messaging v2 or the newer Notify feature provides the
  better approved path. Notify adds at least USD 0.045 per message and is therefore
  not recommended unless its managed compliance path is required;
- the exact tax/currency effect on the project bill;
- actual price, part count and delivery status from the controlled Swiss sends.
