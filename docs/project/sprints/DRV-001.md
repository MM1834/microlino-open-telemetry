# DRV-001 — Fahrtenbezogene Live-Ansicht

**Status:** Complete — backend deployed and productive road test accepted

**Started:** 2026-09-10

## Objective

Provide a dedicated, smartphone-first and glanceable page for the currently
running journey. It emphasizes current consumption or regeneration, a larger
power bar, remaining range both to zero SOC and to the configured SOC reserve,
and a combined speed/power diagram for exactly the current journey.

## Accepted product decision

The view is **fully journey-related**. Its chart boundary is not the moment at
which a browser page was opened. The authenticated Vehicle API reads the
canonical active journey ID and start timestamp already maintained by the
notification session state, then returns native one-minute Speed and Power
History points since that boundary. Reloading the page or changing device can
therefore resume the same running journey.

## Scope

- separate authenticated `/dashboard/drive/` page;
- read-only vehicle selection and live AWS snapshot/WebSocket updates;
- large current kW value and enlarged mode-specific power bar;
- estimated range to 0% and to the user's configured SOC reserve;
- combined current-journey speed/power diagram without interpolation over gaps;
- JWT and active vehicle-assignment enforcement identical to snapshot/History;
- inactive and unavailable journey states that fail safely.

## Explicit boundaries

- no driving controls or interactive chart controls;
- no new firmware topic and no change to telemetry ingestion;
- no location data in the new endpoint;
- the notification table remains private; the browser only sees the minimized
  Vehicle API projection;
- a stale journey is query-bounded to 24 hours;
- AWS deployment and hosted acceptance remain separate release gates.

## Implementation state

The repository contains the completed backend and portal implementation. The new
`current-journey` route reads only the canonical journey record and the existing
Speed/Power History partitions. The portal page consumes that route, appends
fresh live values in memory, segments the Speed curve across reception gaps and
uses existing personal range settings/forecast.

Reviewed Change Set `drv-001-current-journey-20260910` added only the new JWT
route and modified the existing Vehicle API Lambda, integration and read-only
IAM policy without replacement or deletion. Stack `mot-aws-3-1` reached
`UPDATE_COMPLETE`; the Lambda is `Active`/`Successful`, reads the exact
`mot-dev-notification-sessions` table, and the new route reports JWT authorization.
An anonymous request returns `401`. The maintainer accepted the hosted layout
without journey points. The first road test then confirmed the journey boundary,
current Speed, both range figures and the overall smartphone layout. It exposed
three portal-only follow-ups: the periodic server refresh replaced short-lived
browser Power points, flow direction was not explicit enough and the page did
not load the persisted portal language. The repository fix now merges refreshed
native History points into the current in-memory journey by timestamp, displays
consumption with `−`, displays charging/recuperation with `+` and green text,
and consumes the shared `mot-dashboard-language` i18n path. Productive testing
accepted these corrections and reload continuity.

The accepted follow-up retains the last completed journey after the backend
clears its active session. The Vehicle API derives its stable start boundary
from `last_completed_journey_id`, bounds the query at completion and returns the
last actual Speed/Power sample as the displayed end. The portal labels this
`Letzte Fahrt · beendet um hh:mm`, preserves its locally denser live points when
the same journey is refreshed, and replaces it only when a different active
journey ID begins. Consumption is again shown without a large sign; green `+`
remains for recuperation and charging.

Reviewed Change Set `drv-001-last-journey-20260910` modified only the existing
Vehicle API Lambda and its integration, both without replacement. Stack
`mot-aws-3-1` reached `UPDATE_COMPLETE`; Lambda health is successful and the
anonymous current-journey request remains `401`.

The accepted follow-up retains the most recently completed journey until the
backend reports a different active journey ID. When no journey is active, the
same protected endpoint now uses the existing persisted
`last_completed_journey_id` and completion timestamp to reload its bounded
Speed/Power History. The portal labels it `Letzte Fahrt · beendet um hh:mm`,
keeps locally collected sub-minute points while the journey ID matches and
replaces it automatically when the next journey starts. Consumption returns to
an unsigned magnitude; the green `+` presentation remains for recuperation and
charging. Power uses compact colored bars: persisted History intentionally has a
cost-efficient one-minute cadence, while an open live page supplements it with
denser browser-local samples. A completed journey remains readable with colored
Speed/Power values inside a muted grey card. The backend revision is deployed,
and productive smartphone testing accepted the live chart, completion transition,
retained last journey and start of a subsequent journey.
