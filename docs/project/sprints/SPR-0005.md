## Objective

Prepare a small ESP32-WROOM AWS beta fleet while implementing the minimum secure
portal boundary for users to access only their assigned vehicles and devices.

Parallel workstreams have independent code and validation lanes. They converge at
one release gate; progress in one lane does not authorize beta release without the
other lane.

## SPR-0005.A — Credential safety

- ignore WROOM `data/aws/**` while retaining `.gitkeep`;
- verify representative CA, certificate, private-key and metadata names are ignored;
- confirm only placeholders are tracked in credential/staging directories;
- make the upload tool reject mismatched `device.json.thingName`;
- restrict or validate the WROOM upload environment;
- do not copy, print, upload or rotate real credentials in this work package.

## SPR-0005.B — WROOM build evidence

`esp32dev-aws` is the one intended beta artifact. GPS is optional runtime hardware,
so GPS and no-GPS require two hardware cases, not separate production firmware.
`esp32dev-gps-test` is retired diagnostics; `esp32dev` is optional legacy regression.

- run a clean compile-only AWS build;
- record commit, PlatformIO/toolchain versions, firmware version, binary SHA-256
  and result;
- do not use `upload`, `uploadfs`, `buildfs`, `erase` or a serial monitor;
- do not build a filesystem while credential staging contains files.

## SPR-0005.C — Device validation

Use the beta provisioning and release checklists. Validate GPS and no-GPS states,
CAN, WiFi/fallback, local WebUI, AWS telemetry, backup, password-protected OTA and
recovery. Flashing, vehicle connection, credential upload and AWS mutation remain
explicit stop gates.

## ONB-001.A — Authorization foundation

The first secure slice precedes self-service claiming:

- map Cognito `sub` to `vehicleId` in a `UserVehicleAccess` table;
- begin with controlled administrator assignment and `ACTIVE`/`REVOKED` status;
- list only assigned vehicles; never scan and return all vehicles;
- authorize every REST snapshot and WebSocket subscription server-side;
- default deny missing, malformed, inactive or unassigned access;
- cap WebSocket connection lifetime at the access-token expiry;
- prevent ping/renewal and fan-out from extending access past token expiry;
- add cross-user and guessed-vehicle negative tests.

Revocation propagation for an already subscribed connection must be explicit: check
access during fan-out or disconnect/delete affected connections transactionally.

## ONB-001.B — Controlled onboarding

Detailed execution and acceptance gates are owned by
[ONB-001.B](ONB-001-B.md).

After authorization enforcement:

- model `deviceId` as physical unit, `thingName`/certificate as cloud identity and
  `vehicleId` as the authorization resource;
- add invitation/controlled account creation and administrator assignment first;
- then add an expiring, single-use, high-entropy claim proof stored only as a hash;
- consume the proof and create access atomically;
- define audit, retry, replacement, transfer and revocation behaviour;
- show “no assigned vehicle/onboarding required” in the portal without leaking IDs.

Public self-registration, billing, fleet-wide administration, remote OTA and local
firmware-WebUI onboarding are out of scope.

## Current confirmed risks

- CLOUD-001 authorization-isolation blocker is resolved for controlled development;
- production hosting, onboarding lifecycle, MFA/session policy and broader release controls remain open;
- historical REST documentation claims JWT-claim handling absent from current code;
- CORS description is stale and the declared default remains `*`;
- CLOUD-014: WROOM credential staging lacks an explicit ignore rule;
- the shared WROOM upload path lacks the LilyGO Thing-name metadata validation;
- no automated firmware tests or CI build workflow currently exists.

## Acceptance criteria

- credential staging is safely ignored and metadata/environment mismatch fails closed;
- one WROOM AWS artifact builds reproducibly;
- GPS/no-GPS physical behaviour is evidence-backed without separate firmware lines;
- REST and WebSocket access are restricted by authenticated user assignment;
- WebSocket access cannot outlive the validated token;
- controlled assignment/onboarding has an auditable lifecycle;
- beta provision/revoke/recover/support owners are assigned;
- unresolved risks block release or have explicit bounded acceptance;
- documentation/screenshots match the validated implementation.

## Stop gates

- stop before credential upload, firmware flash, vehicle-bus connection or AWS
  mutation unless explicitly approved;
- stop release to mutually untrusted testers until user-to-vehicle isolation passes;
- stop destructive historical cleanup until relevant Chat-export records exist.
