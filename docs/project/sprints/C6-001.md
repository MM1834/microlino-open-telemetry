# C6-001 — Dual-CAN ESP32-C6 Pilot Platform

> **Status:** Closed — N16 dual-CAN WiFi/AWS pilot qualified; production hardening deferred
>
> **Started:** 2026-08-05

## Objective

Qualify one maintained ESP32-C6 firmware line for compact WiFi pilot adapters with
two physically independent Classical CAN inputs and optional UART GPS. Support the
Seeed Studio XIAO ESP32-C6 and the Muse Lab nanoESP32-C6-N16 development board
through PlatformIO board profiles without duplicating telemetry, decoder, WebUI,
security, AWS IoT or OTA application logic.

The intended pilot benefit is to wire Display CAN and Standard CAN once. Later
publication of verified Standard-CAN identifiers and scaling should require a
decoder/firmware update, not an adapter wiring change.

## Scope boundary

- Both CAN channels are passive telemetry inputs; no vehicle-control workflow is
  introduced.
- Both buses use external 3.3 V-compatible CAN transceivers and independent
  RX/TX pairs.
- Classical CAN at the currently required bitrate is in scope; CAN FD is not.
- USB-C remains the board power and service connection for the pilot assembly.
- WiFi is the operational transport. The external antenna is the preferred XIAO
  vehicle installation, subject to enclosure and cable strain relief.
- `Standard-CAN V1 - Pioneer` exposes only physically confirmed signals plus
  explicitly labelled provisional cell-pair fields. `Standard-CAN V2` shares the
  evidence-backed layout but remains unverified on a V2 vehicle.
- Existing WROOM and LilyGO firmware paths remain supported during qualification.

## Firmware architecture

Create one `firmware/esp32-c6` application with shared application and subsystem
code. PlatformIO selects only the board-specific definition:

| Environment | Board | Board-specific responsibility |
|---|---|---|
| `xiao-esp32c6` | Seeed Studio XIAO ESP32-C6, 4 MB | GPIO map, RF antenna switch, USB mode and 4 MB partitions |
| `nanoesp32c6-n16` | Muse Lab nanoESP32-C6 v1.0, N16 | DevKitC-compatible GPIO map, PCB antenna, 16 MB partitions and dual USB upload paths |
| `xiao-esp32c6-aws` | XIAO plus AWS IoT | Extends the XIAO base profile; no source fork |
| `nanoesp32c6-n16-aws` | nanoESP32-C6-N16 plus AWS IoT | Extends the N16 base profile; no source fork |

Board profiles must expose named capabilities and pins. Application code must not
infer a board from scattered preprocessor checks. Flash partition selection may
differ between 4 MB and larger assemblies while keeping the same configuration and
telemetry contracts.

## Delivery sequence

1. Identify the exact ESP32-C6 development board, antenna variant, flash size and
   accessible GPIOs.
2. Freeze the XIAO pilot pin map and verify that neither USB nor the RF switch
   conflicts with two TWAI pairs and the GPS UART.
3. Add the shared C6 PlatformIO application and the two non-AWS board profiles.
4. Replace the single-instance legacy TWAI integration on the C6 path with the
   handle-based multi-controller API and independent receive diagnostics.
5. Compile both boards and prove simultaneous listen-only reception on two
   electrically separate CAN buses.
6. Add GPS, WiFi, authenticated local WebUI and configuration parity.
7. Add LittleFS/AWS IoT and validate a 4 MB dual-slot OTA partition layout.
8. Run powered hardware acceptance, then freeze the pilot BOM, wiring and
   provisioning instructions.

## Initial XIAO pin candidate

This mapping is a qualification candidate, not yet approved wiring evidence:

| Function | XIAO pin | ESP32-C6 GPIO |
|---|---:|---:|
| Standard CAN RX/TX | D0 / D1 | 0 / 1 |
| Display CAN RX/TX | D2 / D3 | 2 / 21 |
| GPS RX/TX | D7 / D6 | 17 / 16 |
| I2C reserve | D4 / D5 | 22 / 23 |
| SPI reserve | D8 / D9 / D10 | 19 / 20 / 18 |

Final naming must always state signal direction relative to the ESP32 and the
transceiver. Transceiver termination must be measured before connection; a pilot
adapter must not silently add a third 120-ohm termination to an already terminated
vehicle bus.

## Acceptance gates

- both PlatformIO board profiles compile from the same C6 source line;
- detected flash size and the selected partition table agree on each physical
  board;
- two TWAI handles start concurrently in listen-only mode at 500 kbit/s;
- frames injected on one CAN bus never increment the other bus counter;
- each channel retains an independent decoder profile and diagnostics;
- Display CAN continues to decode the currently supported `0x602`, `0x603` and
  `0x604` frames;
- Standard-CAN V1 - Pioneer rejects implausible pack/current/cell samples and
  publishes only evidence-bounded telemetry; Standard-CAN V2 output stays limited
  to the same fields and is clearly distinguished from V2-verified telemetry;
- GPS receives checksum-valid NMEA while both CAN channels and WiFi are active;
- setup AP, authenticated WebUI, configuration backup/restore and local OTA pass;
- the 4 MB layout supports the chosen LittleFS content and rollback-capable OTA;
- AWS X.509 credentials remain per-device and are not included in firmware images;
- a powered soak test shows no repeated resets, bus-off loop or cross-channel
  starvation;
- wiring, antenna, termination, enclosure and provisioning instructions are
  recorded before pilot duplication.

## Started work and current blockers

The two physical XIAO boards were identified from the supplied photographs as
Seeed Studio XIAO ESP32-C6 assemblies with an internal ceramic antenna, selectable
external antenna connector and 4 MB flash. Repository inspection confirmed that
the current ESP32-WROOM firmware uses the legacy single-instance TWAI driver and
only exposes CAN1 at runtime; its configuration schema already reserves a CAN2
profile.

ESP-IDF provides two physical TWAI controllers on ESP32-C6 and a handle-based API
for multiple instances. Photographs identify the connected primary candidate as a Muse
Lab `nanoESP32-C6 v1.0` development board carrying an N16 module and PCB antenna.
It exposes the DevKitC-style GPIO set on two 15-pin headers and provides separate
CH343 USB-UART and native ESP32-C6 USB-Serial/JTAG Type-C ports. A read through the
native port on 2026-08-05 confirmed ESP32-C6 QFN40 revision v0.2, a 40 MHz crystal
and 16 MB SPI flash. The board has no visible external-antenna connector; vehicle
WiFi acceptance must therefore test its PCB antenna in the intended enclosure.
The 16 MB result must not be generalized to later purchases without a per-board
flash check.

## Implemented firmware slice

On 2026-08-05 the new `firmware/esp32-c6` line added:

- pinned Arduino ESP32 3.3.8 / ESP-IDF 5.5.4 PlatformIO tooling;
- `nanoesp32c6-n16` and `xiao-esp32c6` board environments;
- board-specific GPIO definitions, XIAO external-antenna selection and separate
  16 MB/4 MB dual-OTA partition tables;
- two handle-based TWAI instances at 500 kbit/s in listen-only mode;
- independent receive counters, timestamps, errors and decoder assignment;
- CAN1 defaulting to Standard-CAN V1 - Pioneer and CAN2 defaulting to Display-CAN;
- shared Display-CAN, Standard-CAN V1 - Pioneer and Standard-CAN V2 decoder code;
- serial board, flash, pin and five-second CAN-counter diagnostics.

The next offline slice added the shared optional-GPS parser on UART1, preserving
the WROOM states for absent receiver, detected NMEA and valid fix. It also added
provisional Standard-CAN V2 decoding for the supplied `0x18D` and `0x4AD` example
frames: pack voltage, display SOC, two cell voltages and derived min/max/delta.
Teltonika fields without a CAN-ID association or complete scaling remain
deliberately undecoded. CAN1 and CAN2 now load independent decoder profiles from
the existing `mot` NVS namespace and accept any registered profile at runtime.
C6 defaults are CAN1 Standard-CAN V1 - Pioneer and CAN2 Display-CAN; single-CAN
WROOM continues to default its available input to Display-CAN.

Post-slice build evidence:

- `nanoesp32c6-n16`: success, 14,332 bytes RAM and 271,266 bytes application flash;
- `xiao-esp32c6`: success, 14,452 bytes RAM and 280,536 bytes application flash;
- WROOM `esp32dev` regression: success;
- LilyGO `lilygo-t-a7670` regression: success.

Physical GPS detection was completed on the N16 board on 2026-08-06. With the
receiver TX connected to ESP GPIO20 and receiver RX to ESP GPIO21, the shared
parser counted continuously increasing UART characters and checksum-valid NMEA
sentences, reaching 7,973 characters during the observed interval. The module
reported `GPS_DETECTED`; no location fix was expected or obtained in the indoor
test. A subsequent outdoor test under open sky reached and retained `GPS_FIX`,
with checksum-valid NMEA input and the UART count increasing beyond 116,000
characters. Simultaneous GPS/CAN/WiFi coexistence remains pending.

The first physical XIAO ESP32-C6 check followed on 2026-08-06 using the unchanged
shared `xiao-esp32c6` image. Upload identified an ESP32-C6FH4 revision v0.2 with
4 MB embedded flash; bootloader, partition table and application were written and
hash-verified. With GPS TX connected to D7/GPIO17 and GPS RX to D6/GPIO16, the
receiver progressed from checksum-valid `GPS_DETECTED` to `GPS_FIX` during an
outdoor cold-start window and exceeded 59,000 UART characters. Both listen-only
CAN controllers remained stable at zero frames and zero errors without vehicle
input. WiFi was not configured and fallback AP support is not yet implemented, so
this is not WiFi/GPS/CAN coexistence evidence.

A bounded passive decoder check then selected Standard-CAN V2 on CAN1 at runtime
without changing listen-only operation. Both candidate identifiers were present on
the Pioneer bus: pack voltage varied from 53.020 to 53.059 V at 90% SOC, while the
two decoded cell values were 4,081 and 4,078 mV with a 3 mV delta. CAN1 and CAN2
continued with zero receive errors. CAN1 was returned persistently to V1 after the
test. This supports the V2 byte layout on Pioneer but does not yet prove
cross-source SOC equivalence or other-model compatibility.

A controlled charging capture then established distinct Pioneer Standard-CAN
states. `0x18D data[6]` changed from `0x10` awake/unplugged to `0x20` plugged and
remained `0x20` through charging and external-AC removal. Signed little-endian
`data[1..2]` was stably -4 while plugged but idle, rose to 112–118 during a charge
measured at 1,836 W AC input and returned to -4 immediately when AC was removed.
This is strong evidence for separate plugged and active-charge candidates, but a
second power level is required before assigning current or power scaling.

A second charge point occurred naturally during taper at 98% displayed SOC:
762 W measured gross AC input, raw signed `0x18D data[1..2]` of 43–47 and about
53.2 V pack voltage. Both charge points closely fit a provisional 0.3 A/raw-unit
scale, yielding approximately 718 W DC at raw 45 and 1,839 W DC at raw 115.
`data[7]` remained 90 while the Pioneer display showed 98%, so the field must stay
source-specific and must not overwrite Display-CAN SOC.

The natural end-of-charge transition was also captured. Display SOC reached 100%,
AC input fell to 0 W and the display switched off while the signed current
candidate fell from +45 to a stable -3. The plug state remained `0x20`; an
independent AC-deenergized plug/unplug test confirmed stable `0x10` unplugged and
`0x20` plugged. Standard-CAN `data[7]` remained 90 through displayed 100% SOC.

A lower-SOC multi-point charge test on 2026-08-06 promoted the Pioneer
`0x18D data[1..2]` scale from candidate to confirmed charging telemetry. At
49.9–50.5 V, raw ranges 118–121 and 135–139 corresponded to independently
measured 1,809 W and 2,088 W AC input. A second EVSE reported about 2,340 W after
regulation while CAN decoded 46.5 A at about 50.51 V, or about 2,349 W. A failed
charge start returned to the same -4 raw idle offset as an unpowered plugged EVSE
while `data[6]` remained `0x20`. The shared decoder now applies 0.3 A/raw unit,
derives watts, requires more than 2 A for active charging and rejects pack voltage
outside 40–65 V, charge/regeneration above 12 kW, discharge above 25 kW and cell
candidates outside 2–5 V. The asymmetric limits incorporate the later normal-road
AWS evidence, where a coherent approximately 20.9 kW discharge peak exceeded the
original 15 kW symmetric boundary.

Three controlled flat-road captures on 2026-08-06 completed the traction and
regeneration correlation. Acceleration produced negative pack current, while
pedal release immediately produced positive current into the pack. Observed
extrema were -260.4 A / about 12.7 kW traction and +94.5 A / about 4.8 kW
pedal-release regeneration. Light braking increased electrical regeneration to
+155.1 A / about 7.8 kW. The shared decoder now exposes both the physical battery
sign convention and a consumption-positive vehicle-power value for portal,
History and ABRP compatibility.

The same repository slice added common AWS topics for pack voltage, current,
power, status and provisional cell extrema. WROOM, LilyGO and C6 publishers use
the same contract; the generic AWS state path already accepts the topics and the
portal renders them. C6 WiFi station support, per-device LittleFS credential
loading and AWS publication are available in `nanoesp32c6-n16-aws` and
`xiao-esp32c6-aws`. Credentials remain external to firmware images. Repository
build and contract tests pass; physical C6 WiFi/AWS/portal operation is still an
acceptance gate.

Before the first persistent C6 AWS pilot deployment, review the backlog state-
envelope decision. The current scalar publisher can send up to 18 messages per
five-second full sample; validating AWS connectivity with it is acceptable for a
short controlled test, but adopting it as the long-running C6 contract would
unnecessarily multiply Rule, Lambda, DynamoDB and WebSocket operations.

For the next mobile validation, the shared C6 firmware now includes a bounded
RAM-only drive capture. It starts automatically at boot and summarizes CAN1
`0x18D` current/voltage/status candidates, CAN1 `0x37F`, and Display-CAN `0x602`,
`0x603` and `0x604`. The serial commands `drive reset` and `drive dump` permit a
controlled observation window without continuous log traffic or flash writes.
Captured data does not survive reset or loss of USB power.

The road-test preparation extends this with a 600-sample RAM ring buffer at
200 ms resolution. `drive trace` exports the most recent 120 seconds of
synchronized Display-CAN speed and Standard-CAN current/voltage/power data. The
bounded procedure is recorded in
[C6 Pioneer traction and regeneration road test](../../testing/c6-pioneer-road-test.md).

Both C6 environments compiled after this addition: `nanoesp32c6-n16` used 14,796
bytes RAM and 278,540 bytes application flash; `xiao-esp32c6` used 14,916 bytes
RAM and 287,822 bytes application flash. The N16 image was flashed and
hash-verified on 2026-08-06. A post-flash console check returned a valid empty
`drive dump`, zero CAN errors and a detected GPS receiver with a valid fix.

Repository build evidence:

- `nanoesp32c6-n16`: success, 13,916 bytes RAM and 259,196 bytes application flash;
- `xiao-esp32c6`: success, 14,020 bytes RAM and 254,568 bytes application flash.

The `nanoesp32c6-n16` factory image was flashed through native USB on 2026-08-05.
Bootloader, the 16 MB partition table, OTA selector and application were written
and hash-verified. The powered startup log confirmed 16,777,216 bytes of flash and
successful concurrent startup of controller 0 on GPIO0/1 with Display-CAN and
controller 1 on GPIO2/3 with Standard-CAN V1 - Pioneer under the original test
default. With no transceivers
connected, both channels remained at zero frames and zero receive errors during
the observed interval.

The same assembly was then connected through two external transceivers to the
Microlino on 2026-08-05. A 15-second native-USB diagnostic capture showed both
controllers receiving concurrently: CAN1 advanced from 101,072 to 110,732 frames
and CAN2 from 42,458 to 46,517 frames, with zero receive errors on both channels.
This is the first physical simultaneous dual-bus reception evidence. It does not
yet prove cross-channel isolation with controlled frame injection, decode
correctness or long-duration stability.

The observed vehicle wiring establishes CAN1 on GPIO0/1 as Standard CAN and CAN2
on GPIO2/3 as Display CAN. The firmware defaults were corrected accordingly after
this capture and the corrected image was flashed and hash-verified. A post-flash
capture showed CAN1 advancing from 8,678 to 18,342 frames and CAN2 from 3,642 to
7,701 frames, again with zero receive errors on both channels. Persistent
configuration will later permit either supported decoder profile to be assigned
independently to either controller.

Simultaneous GPS/CAN/WiFi coexistence, physical C6 AWS/portal validation,
authenticated WebUI and OTA handlers remain subsequent qualification or
implementation slices.

On 2026-08-06 the N16 qualification device `MOT-E6EBAC` was upgraded to the
current `nanoesp32c6-n16-aws` image. A unique AWS IoT Thing and certificate were
created for `mot-esp32c6-daa280`, restricted to the existing `pioneer` vehicle
topic, and the credential set was hash-verified after LittleFS upload. Firmware
reported `credentials=yes` and correctly waited for network connectivity. The
existing portal assignment for the controlled owner account was confirmed active
without modification. WiFi configuration, first TLS connection, live publication
and hosted-portal observation remain open physical gates.

The following normal-road run closed the first WiFi/TLS/publication gate. The C6
held WiFi and AWS IoT connectivity, published more than 3,000 scalar messages and
the AWS state table received the new pack current/power, vehicle power and
regeneration/discharge fields for `pioneer`. Both CAN counters remained error-free.
After applying the evidence-based asymmetric power bounds, the updated AWS image
was flashed and hash-verified; WiFi, LittleFS credentials and decoder assignments
survived and AWS reconnected successfully. Hosted static-portal deployment and
longer soak remain open.

## Closure decision — 2026-08-06

C6-001 closes as a bounded pilot qualification, not as a general production
approval. The Muse Lab nanoESP32-C6-N16 path passed the sprint's core product
hypothesis: one shared firmware line received Pioneer Standard CAN and Display CAN
concurrently, decoded the evidence-backed battery signals, retained independent
profiles, connected over WiFi with a unique AWS identity and delivered live data
to the authorized portal. Normal-road operation reached 82.5 km/h and about
20.9 kW discharge with both CAN receive-error counters remaining at zero.

The Seeed XIAO profile compiled, flashed on its confirmed 4 MB target and passed
standalone GPS plus dual-controller startup. It was not subjected to the same
vehicle dual-CAN/AWS run and is therefore a compatibility target rather than the
recommended pilot assembly.

Acceptance disposition:

| Gate | Closure status |
|---|---|
| Shared C6 source and all four C6 build profiles | Passed |
| Physical flash size and matching partition table | Passed on N16 and XIAO |
| Concurrent listen-only TWAI at 500 kbit/s | Passed on N16; startup-only on XIAO |
| Simultaneous Pioneer dual-bus reception and independent diagnostics | Passed on N16 |
| Controlled injected-frame cross-channel isolation | Deferred |
| Display-CAN and Pioneer Standard-CAN decoding | Passed within recorded evidence bounds |
| Optional GPS | Passed separately on both boards; not retained in the final N16 road assembly |
| WiFi, per-device AWS X.509 and hosted live telemetry | Passed on N16 |
| Authenticated local WebUI and runtime OTA | Deferred; not implemented on C6 |
| 4 MB rollback-capable OTA runtime | Partition/build capacity passed; runtime update deferred |
| Extended soak, production wiring, enclosure and power qualification | Deferred |

The recommended next pilot hardware is therefore the N16 board, USB powered, with
two external 3.3 V CAN transceivers using CAN1 GPIO0/1 for Standard CAN and CAN2
GPIO2/3 for Display CAN. Devices must be provisioned individually and only one
device should publish the active state of a given portal vehicle at a time.

Deferred gates move to the engineering backlog. Reopening this sprint is not
required unless evidence invalidates the shared decoder or N16 pilot decision.
