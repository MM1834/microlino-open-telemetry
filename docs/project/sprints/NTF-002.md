# NTF-002 — Charging Interruption Notifications

> **Status:** Completed — qualified Ladestopp email accepted; SMS deferred
>
> **Date:** 2026-08-24

## Objective

Notify an opted-in user when an established charging session stops before the
configured target SOC while the vehicle remains plugged in. Reuse the confirmed
NTF-001 email channel and prepare SMS behind an administrator-controlled approval
gate. The notification remains informational and never controls charging.

## Detection contract

A charging-interruption candidate starts only on a fresh transition from
`charging/is_charging=true` to `false` while all of the following are true:

- the same charging session is still `charging/plugged=true`;
- charging was previously observed in that session;
- `is_charging=true` remained continuously observed for at least 45 seconds;
- the latest valid SOC is below the user's configured target SOC;
- the telemetry timestamps cannot roll the state backwards.

The cloud enqueues a delayed validation for 60 seconds. When it becomes due, the
validator sends at most one event only if:

- the vehicle is still plugged in and the charging session identifier is unchanged;
- no newer `is_charging=true` update cancelled the candidate;
- no unplug event ended the session;
- the latest valid SOC remains below the configured target;
- the same user, vehicle and session have not already received this interruption.

Returning to `is_charging=true`, unplugging or reaching the target cancels the
candidate logically; an already queued validation then becomes a no-op. A durable
delayed queue is required instead of relying on a later telemetry message, because
a real interruption may be followed by silence. The queue consumer must read the
authoritative DynamoDB session state before delivery.

This contract detects a reported charging stop. It cannot infer an interruption
when the adapter or network disappears before the `true → false` transition is
received; offline/device-health notification is a separate problem. Very short
charger pauses under 60 seconds are intentionally suppressed.

The first physical acceptance showed a real short charger-start attempt followed
by a stop and email. Based on that evidence, the detector now arms only after at
least 45 seconds of continuously observed charging. Any `false` transition resets
the qualification; a later `true` begins a new 45-second window. This interval is
measured from cloud-observed telemetry and therefore fails closed when a short
`true` pulse falls entirely between uploads.

## User preference

The pilot adds a separate default-off `chargingStopEmailEnabled` preference and a
separate `chargingStopThreshold` (default 80%). Reaching the normal SOC target and
stopping below the Ladestopp target can therefore be configured independently.
Delivery reuses the user's already confirmed notification email destination; no
third address is introduced. The message includes `vehicleId`, last SOC, Ladestopp
target and the 60-second persistence statement. It says **Ladevorgang gestoppt**,
not that a charger fault is proven: the same signal sequence can also result from
a deliberate stop or external load management.

## SMS authorization boundary

SMS requires all of these independent gates:

1. AWS End User Messaging SMS service access is active in the deployment region;
2. an operational destination/origination path is approved for the target country;
3. a small account spend limit and alarm are configured;
4. the preference has an administrator-owned `smsApproved=true` flag;
5. the user has explicitly enabled SMS and the normalized E.164 destination is
   verified under the applicable AWS mode.

The authenticated user preference API must never be able to set
`smsApproved`. Disabling SMS remains self-service; enabling delivery is effective
only when both user opt-in and administrator approval are true. Initial rollout is
an explicit allowlist, not open SMS self-service.

## Current AWS evidence

On 2026-08-24 the account is billable, but SMS access is not active in
`eu-north-1`. `sns get-sms-attributes` returned a service-subscription error and
all three AWS End User Messaging SMS account, limit and spend-limit reads returned
`SubscriptionRequiredException`. Moving the AWS account out of the Free plan did
not itself subscribe or enable the SMS service. No SMS send is claimed.

## Deployment evidence

On 2026-08-24 51 focused notification/journey tests and 18 portal contract tests
passed with JavaScript/Python syntax and whitespace validation. The reviewed
Change Set `mot-ntf-002-charging-stop-20260824` added only an encrypted delayed
SQS queue, encrypted dead-letter queue and Lambda event-source mapping, and
updated the existing Lambda code, minimal queue IAM permission and Preference API
in place. Existing tables, SNS topic, IoT rule, Journey finalizer and APIs were not
replaced. The stack reached `UPDATE_COMPLETE`, the mapping is enabled and the
queue has a 60-second visibility timeout, one-day retention and three-attempt DLQ
redrive.

A read-only live Preference API invocation for the controlled `pioneer` owner
returned the existing SOC and journey settings unchanged plus the new default-off
`chargingStopEmailEnabled=false` and independent
`chargingStopThreshold=80`. A deliberately invalid delayed validation probe
returned zero deliveries without error. No physical charging-stop delivery is yet
claimed at that checkpoint.

The first physical startup sequence then supplied a brief cloud-observed charging
state followed by `false` while still plugged at 89% against a 100% Ladestopp
target. The delayed validator stored exactly one `CHARGING_STOP` event, dispatched
one email and emptied the queue; the maintainer confirmed receipt. Because this
was an unwanted startup interruption, the result justified the 45-second
continuous-charging qualification. A second reviewed Change Set modified only the
two existing Lambda code packages in place and reached `UPDATE_COMPLETE`. The
detector now resets qualification on every false transition, and the idempotency
key limits Ladestopp delivery to one per user, vehicle and plugged session.

The final controlled `pioneer` test began a new plugged session, remained
cloud-observed as charging for more than the required 45 seconds and then stopped
at 91% against the owner's independent 100% Ladestopp target. The session stayed
plugged and not charging throughout the delayed window. The queue contained
exactly one delayed message, the 60-second validator stored exactly one
`CHARGING_STOP` event with status `DISPATCHED`, SNS accepted one email and the
queue returned empty without Lambda errors. The maintainer confirmed receipt.
This closes the NTF-002 email scope. The updated hosted UI had already been used
to enable the preference; its final explanatory wording adds the visible
45-second qualification and remains a static-file refresh only.

## Acceptance

- a `true → false` transition followed by 60 seconds plugged and not charging
  below target sends exactly one email;
- a restart within 60 seconds sends none;
- unplugging within 60 seconds sends none;
- reaching the target before validation sends none;
- startup already not charging sends none;
- replayed or out-of-order telemetry sends none;
- two users on one vehicle are evaluated against their own target and opt-in;
- existing target-reached and journey notifications remain unchanged;
- SMS cannot be enabled by an ordinary user or sent without every server-side gate.
